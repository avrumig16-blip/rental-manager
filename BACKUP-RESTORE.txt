ManageRent4U V10.22.42 — backups and quick updates

ONE-TIME BACKUP SETUP
1. Upload this version, replacing the old API folder. There are 5 API functions.
2. In Supabase SQL Editor, run setup/BACKUP-SETUP.sql once as the project owner. This creates protected backup settings/jobs, a private backup bucket, a transactional snapshot function and a worker that runs every five minutes. The worker does nothing until its server configuration is saved.
3. Set APP_BASE_URL in Vercel to your deployed HTTPS website URL, without a trailing slash. Set a long random CRON_SECRET. Keep SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, RESEND_API_KEY and your verified RESEND_FROM_EMAIL. Redeploy after changing environment variables.
4. Open Settings > Backup. Each signed-in profile can create a downloadable backup and set its own backup email. Opening Backup registers the trusted server worker URL and secret when configured. Saving an enabled schedule also verifies that configuration. The secret stays in the server/database; it is never returned to the browser or included in a backup.
5. Test Create downloadable backup, download and verify the ZIP. Then test Email backup now. Finally enable a schedule such as every 2 days, 3 weeks, 1 month or 1 year. The first scheduled send is one full interval after you enable/change the frequency. The worker checks every five minutes; generation and provider delivery take additional time. Calendar months/years retain the original day when possible and clamp to the last day in shorter months.
6. Check Supabase Cron > managerent4u-backup-worker and its execution history if automatic delivery does not arrive. Supabase must remain active. A paused project cannot run the worker. Check Resend delivery logs for bounced or rejected emails.

BACKUP CONTENTS
Platform administrators always receive the entire site's public application tables and all stored object files (excluding earlier backup archives and temporary jobs). Other profiles receive the records/files in their owned or permitted accounts, with building restrictions enforced again by the server. This includes all stored columns, notes, private agreements, costs, payment accounts and entries, utility details, contracts/intakes, messages, message events, inline attachments, reminders, indexations, expenses, sharing records where permitted and profile/settings metadata. Tables are discovered dynamically, so new public workspace tables are included for whole-account backups. Building-restricted rows are filtered by their tenant/unit/building/payment/message/utility/owner links; unknown unlinked rows are excluded to protect privacy.
Actual Supabase uploads are copied into storage/ with their original bucket/path. Incoming-email attachments are retrieved from Resend where still available and copied into incoming-email/. Existing inline/base64 attachments remain in their original database fields. Application code, assets and templates are included under application/. Administrator exports additionally contain schema metadata for public columns, constraints, indexes, functions, policies and triggers. Every ZIP contains a manifest with row counts, file sizes and SHA-256 checksums. A missing referenced uploaded document or failed file download visibly fails the job, and can be retried; it is never labelled a complete backup silently.
The database snapshot is transactional. File bytes are copied afterward, so avoid changing/deleting uploads during generation. Already-deleted documents and expired/unavailable external email attachments cannot be reconstructed. Arbitrary third-party URLs are preserved in their records rather than downloaded. Authentication profiles/role metadata are exported; passwords, active sessions, hosting secrets and external banking-provider state are excluded. Stored bank connection identifiers remain in the records, but provider consent may require reconnection. Preserve your Vercel/Supabase configuration separately and reconnect banking if required.
This is a comprehensive APPLICATION backup/export. It is not a physical PostgreSQL disaster-recovery image. Keep native Supabase/PostgreSQL backups and migration history too, especially for authentication identities, schema creation, custom non-public schemas, platform infrastructure and a fresh-project restore.

DOWNLOADS AND EMAILS
Generation is resumable: you can leave the page and the scheduled worker continues the job after setup. Return to Settings > Backup to check progress, failures and the latest archives. Download links are private and expire after five minutes; request a new one if needed. Permissions are rechecked for generation and each download. A changed profile scope requires a new backup.
Backups up to 10 MB arrive as one ZIP attachment. Larger archives arrive in numbered emails, each with a ZIP volume containing a binary segment and reassemble.py. Extract every volume into the same folder and run reassemble.py to reconstruct the complete backup.zip. The website Download button always returns the full single archive. Provider size/rate limits may delay email delivery; saved archives remain downloadable.
Archives and cached generation files are retained in the private mr4u-backups bucket until the project owner removes them. Backups use storage space. Default raw backup size limit is 256 MB; increase BACKUP_MAX_BYTES and the backup bucket's file_size_limit if your data grows beyond that, within your hosting memory/runtime limits. A size-limit failure is shown explicitly.

VERIFY AND RESTORE
Extract or leave the ZIP intact. Run: python restore-backup.py your-backup.zip
This validates ZIP CRCs, manifest SHA-256 checksums and file sizes, prints the inventory and makes NO remote changes.
For recovery, use a staging Supabase project with the compatible application schema and correctly mapped auth identities first. Set SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY for that TARGET project. Read the script before running: python restore-backup.py your-backup.zip --apply
It upserts exported rows in dependency order and restores Supabase object bytes. It does not delete newer records, recreate missing tables or change schema. Fix any missing schema/identity dependency before retrying. --tables selects a comma-separated subset. --restore-profiles updates metadata for existing exported auth identities; it cannot reconstruct passwords. Scheduled emails are disabled during restore unless --restore-schedules is explicitly supplied. Profiles from another project require careful identity mapping before data restoration.
Validate totals, uploaded document downloads, messages and permissions before using the recovered project. Source assets are under application/ for redeployment. Administrator schema metadata is a recovery reference; keep the original schema migrations for a fully reproducible fresh install.

QUICK UPDATE FIXES
Active dialogs now receive live record data. Confirmed payment/message saves update their shared state immediately, while full refresh runs in the background. Refreshes retain existing tables instead of briefly resetting message/utility tables. Payment status calculations issue independent reads in parallel. Save/send success waits for actual server confirmation, but no longer waits for the entire workspace reload. External provider, cold-start and network latency can still affect the actual save/send duration.
