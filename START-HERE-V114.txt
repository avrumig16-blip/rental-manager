MANAGERENT4U V10.22.114 — COMPLETE RELEASE

INSTALLATION
1. Back up the existing app/database. Extract the complete ZIP. Replace all project files in the same repository root, preserving the api, lib, assets and setup folders. Keep the existing Supabase project and Vercel environment variables.
2. Let the Vercel deployment finish. No new Vercel function or extra built-in cron job is added. The existing Vercel daily cron remains a fallback and uses the same eligibility checks.
3. In Supabase SQL Editor, run the ENTIRE setup/V10.22.114-SETUP.sql file once. It applies both capacity enforcement and the new background bank scheduler. If upgrading a database that still lacks V112 tenant/address fields, run setup/V10.22.112-TENANT-REPAIR.sql as well; V114 does not replace that repair.
4. Open Banking once as a user whose plan includes banking. This stores/refreshes the existing worker URL and matching CRON_SECRET. Then no open browser is needed. Vercel CRON_SECRET and the saved worker secret must match. Keep the existing production domain accessible to the database worker (Vercel deployment protection must not block it).
5. In Settings > Rent & payment defaults, enable automatic bank checking and save. Keep each required bank connection connected and select the accounts to read. If consent expires, reconnect with the bank.

VERIFY AFTER INSTALLING
- Supabase > Cron: managerent4u-bank-schedule114 should be active, with schedule */5 * * * *. The old managerent4u-bank-daily103 job is replaced; other jobs are untouched.
- Check that the stored worker is configured without displaying its secret:
  select id, url is not null as url_set, secret is not null as secret_set from public.mr4u_receipt_worker_config where id=true;
- Bank rounds become due at 06:00, 12:00 and 18:00 Europe/Brussels. The queue is checked every five minutes, sending up to six distinct due connections per tick. A tick with no due bank makes no HTTP calls. Larger queues and interrupted imports continue on later ticks.
- Check Banking's last successful check after each round while the browser was closed. Failures and partial reads do not advance the successful timestamp. External bank availability and valid consent remain required.
- Browser-independent scheduling requires the Supabase database to be running; a paused/offline project cannot run its jobs. Function usage and provider quotas still apply.

PLAN RULES
- Basic: 2 units, 2 current/upcoming tenants, 1 building, 1 owner, existing user allowance and existing bank permission.
- The tenant allowance always equals the unit allowance. Ended/inactive or archived tenants remain in history and do not count. A future start counts; a future end notice still counts until it ends. An expired contract end date alone does not end a tenancy.
- All owner/building/unit rows count, including archived records. Existing records are not deleted. Already-over-limit workspaces can view/edit them; new records and tenant reactivations are blocked until capacity is available or the plan is upgraded.
- Subscriber administration allows separate building and owner limits. Zero means unlimited. Existing plans above 2 units retain unlimited buildings/owners until explicitly set by the platform administrator; V114 does not silently downgrade these subscriptions.
- Normal customers cannot raise their own limits. Database triggers cover direct writes, imports, tenant save RPCs, reactivation and workspace moves. Simultaneous growth is serialized by a workspace row update.
